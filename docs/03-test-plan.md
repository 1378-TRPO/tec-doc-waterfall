# Test Plan — «Календарик»

**Версия:** 1.0  
**Основание:** `docs/01-srs.md` v1.0 и `docs/02-design-doc.md`  
**Ответственный:** QA (участник 4)  
**Статус:** подготовлен для Gate 3; выполнение и результаты фиксируются на Gate 4.

## 1. Цель и границы тестирования

Цель — вручную подтвердить acceptance criteria SRS для MVP «Календарика». Проверяются REST API, сохранение данных в PostgreSQL и пользовательские сценарии React-интерфейса после его появления.

В тестирование не входят функции вне scope SRS: email/push/WebSocket-уведомления, внешние календарные API, видеозвонки, повторы, часовые пояса, приватные календари, drag-and-drop, мобильная вёрстка и UI-автотесты.

## 2. Среда и порядок прогона

- PostgreSQL 16 запускается командой `docker compose up -d db` из репозитория backend.
- Backend запускается по инструкции в его `README.md`; перед первым запуском применяются миграции.
- Frontend запускается по своей инструкции после его реализации.
- API проверяется через Swagger UI в Development-окружении или Postman с заголовком `Authorization: Bearer <JWT>`; пользовательские сценарии — вручную в браузере.
- Перед каждым полным прогоном используется чистая БД либо явно отмечается сохранённое состояние тестовых данных.
- Время начала и конца передаётся в ISO 8601 UTC. Для сценариев ниже `T` — завтрашняя дата, чтобы запись считалась будущей.

## 3. Тестовые данные

| Роль | Пользователь | Учётные данные | Назначение |
|---|---|---|---|
| Организатор | Alice | `alice@local` / `alice123` | Создаёт, редактирует, отменяет встречи, проверяет RSVP. |
| Участник 1 | Bob | `bob@local` / `bob123` | Принимает приглашение и получает уведомления. |
| Участник 2 | Carol | `carol@local` / `carol123` | Остаётся `pending` или отклоняет приглашение; нужна для проверки нескольких статусов. |

Базовая встреча: «QA: планирование», начало `T 10:00Z`, конец `T 11:00Z`, ссылка `https://meet.local/qa-demo`, участники Bob и Carol. Организатор не добавляется в список участников.

## 4. Набор тест-кейсов

| ID | FR | Сценарий и краткие шаги | Ожидаемый результат | Готовность на Gate 3 |
|---|---|---|---|---|
| TC-01 | FR-1 | Войти Alice с корректным паролем; отдельно войти с неверным паролем. | При успехе выдан JWT и доступна текущая учётная запись; при ошибке — понятный ответ 401. | Можно выполнять на API. |
| TC-02 | FR-1 | Вызвать защищённый endpoint без JWT и с JWT Alice. | Без токена — 401; с токеном доступ разрешён только Alice. | Можно выполнять на API. |
| TC-03 | FR-2 | Alice создаёт запись; Alice и приглашённый Bob запрашивают календарь на диапазон, включающий `T`. | Запись возвращается организатору и участнику, но не постороннему пользователю; на UI отображается в календаре. | Готов к API- и ручной UI-проверке. |
| TC-04 | FR-3 | Создать личное событие с корректными обязательными полями. | Ответ 201; запись видна организатору и не содержит участников или ссылки. | Можно выполнять на API. |
| TC-05 | FR-4 | Создать базовую встречу с Bob и Carol; открыть карточку под Alice. | Ответ 201; участники сохранены со статусом `pending`, ссылка и поля встречи доступны. | Можно выполнять на API. |
| TC-06 | FR-5 | По отдельности отправить пустой заголовок, `endAt <= startAt`, ссылку без `http://`/`https://`; повторить через форму. | Ответ 400/ошибка формы; некорректная запись не появляется. | Готов к API- и ручной UI-проверке. |
| TC-07 | FR-6, FR-7 | Bob принимает приглашение; Carol отклоняет его; Alice открывает карточку. | Bob видит встречу и может изменить свой ответ; Alice видит `accepted` и `declined` у участников. | Можно выполнять на API. |
| TC-08 | FR-6, FR-7, FR-12 | Проверить запреты: Carol не редактирует/не отменяет/не пингует; Alice не отвечает RSVP за Bob; участник без доступа не читает карточку. | Для запретных действий возвращается 403; данные не изменяются. | Можно выполнять на API. |
| TC-09 | FR-8 | Alice пингует Bob по базовой встрече. | В дополнение к уведомлению `invited`, созданному при приглашении, у Bob появляется новое непрочитанное уведомление типа `pinged`. | Готов к API- и ручной UI-проверке. |
| TC-10 | FR-9 | Создать приглашение, затем пинг/изменение/отмену; под Bob проверить счётчик, список и отметку прочитанным. | Уведомления имеют ожидаемые типы; число непрочитанных меняется; после отметки запись прочитана. | Готов к API- и ручной UI-проверке. |
| TC-11 | FR-10 | Создать будущую, прошлую, отменённую и отклонённую Bob встречу; запросить ближайшие. | Возвращаются только будущие доступные записи по времени; отменённая и отклонённая не попадают в список. | Готов к API- и ручной UI-проверке. |
| TC-12 | FR-11 | В форме встречи нажать «Сгенерировать демо-ссылку». | В поле подставлена строка `https://meet.local/<8 символов>`; ссылка проходит валидацию и кликабельна после сохранения. | Готов к ручной UI-проверке. |
| TC-13 | FR-12 | Alice изменяет встречу, затем отменяет её; повторно пытается изменить/отменить/пинговать. | Изменение и отмена доступны только организатору; отменённую встречу нельзя менять, повторно отменять или пинговать; UI показывает её зачёркнутой. | Готов к API- и ручной UI-проверке. |
| TC-14 | FR-13 | Создать базовую встречу, выполнить RSVP и создать уведомление; перезапустить backend и повторно войти. | Встреча, статусы RSVP и уведомления сохраняются в PostgreSQL. | Готов к API-проверке. |

## 5. Сценарий приёмочного прогона

1. Войти как Alice и создать базовую встречу.
2. Войти как Bob, убедиться, что встреча видна, и выбрать `accepted`.
3. Вернуться под Alice, открыть карточку и проверить RSVP Bob.
4. Пинговать Bob; под Bob проверить непрочитанное уведомление и отметить его прочитанным.
5. Изменить и отменить встречу; проверить уведомления `changed` и `cancelled`.
6. Перезапустить backend, повторно войти и убедиться, что данные сохранены.

UI-части шагов 4–5 выполняются после реализации frontend. Если функция отсутствует в проверяемой сборке, в Test Report указывается статус `Blocked` и ссылка на зависимость, а не `Failed`.

## 6. Критерии входа и выхода

**Вход в Gate 4:** backend и frontend собираются без ошибок, миграции применены, есть доступ к трём seed-пользователям, известна проверяемая версия сборки.

**Выход из Gate 4:** все acceptance criteria SRS имеют результат `Passed`, либо согласованный блокер/дефект зафиксирован в `docs/04-test-report.md`; критичных дефектов нет.

## 7. Отчётность по дефектам

Для каждого дефекта фиксируются: ID, дата, версия сборки, предусловия, шаги воспроизведения, фактический и ожидаемый результат, серьёзность (`Critical`/`Major`/`Minor`), статус и ссылка на соответствующий тест-кейс.
